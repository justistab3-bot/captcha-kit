# captcha-kit

固定点阵字体验证码的识别工具箱。**两条通道**：原图走像素精确匹配（结果带完备性证明），
缩放截图走归一化 + DP 联合切分识别。不依赖任何深度学习框架。

>这个仓库针对的是 ddddocr识别不出来的那些，比如说有干扰线、花字那种，需要自己手动拿五六个样本验证码，建立模板后一个验证码识别所需时间大概是 3ms！


> **它解决什么**：有一类验证码用的是**固定点阵字体** —— 同一个字符在任意两张图里
> 逐像素完全相同。对这类验证码，训练 CNN 是杀鸡用牛刀；直接做模板匹配更快、更准，
> 而且能给出"这次识别为什么是对的"的证明。
>
> **它不解决什么**：扭曲、粘连、随机旋转、手写体这类验证码，请老老实实上模型。

```python
from captcha_kit import TemplateSet, read, arithmetic

ts = TemplateSet.from_labeled([(图片字节, "13+15="), ...])[0]   # 从标注样本建模板
result = read(图片字节, ts, validate=arithmetic.is_arithmetic)
expr, answer = arithmetic.evaluate(result.text)      # ('13+15', 28)
```

## 快速开始

```bash
# 1) 先探查：把一批图里的字形聚成簇，看看字体是不是固定的
captcha-kit discover samples/

# 2) 建模板：需要一份「图片 + 标准答案」的标注
captcha-kit build samples/ -l labels.csv -o templates.json

# 3) 识别
captcha-kit read captcha.png -t templates.json -a            # -a 表示算术验证码
captcha-kit read samples/ -t templates.json -a -c            # -c 纯净模式：只输出答案
```

`labels.csv` 每行是 `文件名,答案`：

```csv
001.png,13+15=
002.png,7+3=
```

也可以不写 CSV：把答案放进文件名（`13+15=__001.png`）即可。

跑一遍端到端演示（全程用仓库自带的合成数据，不需要任何真实验证码）：

## 工作原理

### 通道 1：像素精确匹配（`mode="exact"`）

字体逐像素固定 ⇒ 正确解只有一个。所以这里不设相似度阈值，而是要求：

1. 每个模板放上去必须与图**逐位相等**；
2. 所有前景像素**恰好被模板覆盖，一个不多一个不少**。

任意一条不满足就判定无解。满足即得到证明，输出里的 `覆盖 158/158` 就是这个意思 ——
它不是"置信度很高"，而是"这就是唯一解"。

推进逻辑利用了一个字体性质：每个字形的首列和末列都有前景像素，所以"剩余第一个有内容的列"
必然是下一个字形的起始列（`check_edge_columns()` 会校验这一点）。

### 通道 2：归一化 + DP 联合切分识别（`mode="scaled"`）

**什么时候需要它。** 站点常把验证码原图按另一种尺寸显示，比如 100×24 显示成
`width:139px;height:56px`，浏览器按 1.39×2.33 **非等比**放大并插值；截图还会再叠一层
系统 DPI 倍率。字符边缘被抹成一堆中间色，"逐像素相等"的前提就没了，通道 1 必然无解。

**为什么不能靠"列空隙"切字。** 这是踩过的坑：放大后一个字会被抗锯齿切成好几段
（`6+5=` 切成 7 段），缩小后相邻字又会粘在一起（`10+14=` 并成 4 段）。实测空隙法
**切字错误率极高，而认字错误率为 0** —— 瓶颈完全在切分，不在识别。

所以通道 2 把切分和识别一起解：

* **纵向**：内容带高度是已知常数（`TemplateSet.band_height`），直接归一化掉纵向缩放；
* **横向**：枚举"规范总宽度 W"，把整条内容缩到 `(band_height, W)`，用 **DP** 在整条上
  求最优模板序列，取契合度最高的 W。

不需要知道原始缩放比，也不需要猜任何阈值。

**契合度用的是前景模糊 IoU**：`Σ(c·t) / (Σc + Σt − Σ(c·t))`。

这个指标换过一次。最初用 `1 − mean|c − t|`，结果 0.5 倍缩小时 **10/10 全部给错答案** ——
因为字模大部分区域是背景，逐像素一致率把背景也算进去，错的字形照样拿 0.8+。
换成 IoU 后背景不贡献分，只有前景真正重叠才有分。

两个求和都向量化：`Σc` 是窗口和（前缀和滑窗），`Σ(c·t)` 是模板前景点处的位移相加。

阈值 `min_agree`（单字形最低 IoU）默认 **0.65**。实测对照（合成数据，20 张/档）：

| min_agree | 2.0× | 1.68× | 1.39× | 1.5× | 1.2×1.6 | 0.8× | 0.5× |
|---|---|---|---|---|---|---|---|
| 0.75 | 15/20 | 20/20 | 20/20 | 20/20 | 17/20 | 0/20 | 0/20 |
| **0.65（默认）** | **20/20** | **20/20** | **20/20** | **20/20** | **20/20** | **20/20** | **0/20**，零错答 |
| 0.55 | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 | 19/20（开始乱猜） |

0.75 会让轻度模糊的图漏判，0.55 会在信息已丢失的图上开始硬猜。0.65 两头都不碰。

### 底色与前景

先取图片的**众数颜色**当底色（验证码底色基本都是一整块平涂，深色底、白底都能应对），
然后以前景与底色的最大通道差算强度，再按 95 分位归一化到 0~1。

归一化是为了**对对比度免疫**：浅灰字配白底、纯红字配深底，归一化后强度分布一样。
另外全程**不做二值化**，因为抗锯齿和插值产生的中间色正是缩放后还能认出来的关键。

## 用自己的验证码建模板

1. **收集样本**：抓一批图，把每张的正确答案记下来（人眼读，通常几十张就够）。
2. **先探查**：`captcha-kit discover samples/`。
   如果簇数接近字符种类数、每簇出现次数都不少，说明字体是固定的，这条路走得通。
   如果同一字符出现多个不同的簇，说明字体不固定 —— 换通道 2 或改用模型。
3. **建模板**：`captcha-kit build samples/ -l labels.csv -o templates.json`。
   构建时会强制校验「一个位图只对应一个字符、一个字符只对应一个位图」，
   不满足就报错（这正是在帮你确认字体是否固定）。有噪点或标注错的样本会被跳过并列出。
4. **验证**：`captcha-kit read samples/ -t templates.json`，看是否全部 `mode=exact`。

## Python API

```python
from captcha_kit import TemplateSet, read, arithmetic
from captcha_kit.templates import discover, render_bitmap

ts = TemplateSet.from_labeled(samples)[0]      # samples = [(bytes, 答案), ...]
ts.save("templates.json")
ts = TemplateSet.load("templates.json")

result = read(image_bytes, ts, validate=arithmetic.is_arithmetic, min_agree=0.75)
result.text          # '13+15='
result.mode          # 'exact' | 'scaled' | 'fail'
result.provable      # True 表示走通道 1，结果带完备性证明
result.confidence    # 通道 2 的 IoU 契合度；通道 1 恒为 1.0
result.covered       # 通道 1：被模板覆盖的前景像素数
result.total         # 通道 1：前景像素总数

arithmetic.evaluate("13+15=")     # ('13+15', 28)
arithmetic.safe_eval("13+15")     # 28  —— AST 白名单求值，不用 eval
arithmetic.is_arithmetic("13+15=")  # True，可直接当 validate 回调
```

`validate` 是个可选回调，用来在多个候选宽度里挑出语义合法的解。不想用算术的话传
自己的谓词即可（比如要求结果符合某个正则）。

测试和示例全部基于它 —— 所以**跑测试不需要联网，也不含任何真实验证码样本**。

## 实测结果

合成数据集，60 张样本建模，字符集 `0-9 + =`（12 个字形，内容带高 21 px），20 张测试：

| 输入 | 正确率 | 通道 |
|---|---|---|
| 原图（可证明） | 60/60 | 通道 1，~3 ms/张 |
| 放大 1.68×2.75 | 20/20 | 通道 2 |
| 放大 1.39×2.33 | 20/20 | 通道 2 |
| 放大 1.5×1.5 | 20/20 | 通道 2 |
| 放大 2.0×2.0 | 20/20 | 通道 2 |
| 放大 1.2×1.6（又小又非等比） | 20/20 | 通道 2 |
| **缩小 0.5×** | **0/20，零错答** | 通道 2 主动拒绝 |

最后一行的意思是：字形只剩几个像素、信息已经不可恢复时，它**拒绝作答而不是硬猜**。
对验证码识别来说，这一点比正确率更重要。

复现：`python examples/demo.py` 与 `pytest`。

## 已知边界

* **要求固定点阵字体**。字体一换（不同版本、不同渲染引擎、不同字号）模板就失效，
  需要重新建。构建时的强制校验会第一时间告诉你这件事。
* **要求固定基线**。字形必须都画在同一条基线上；`offsets` 支持同一字符出现在多个
  不同高度，但每个字形自身的形状不能随位置变化。
* **通道 2 是概率性的**。模糊、形变严重时正确率会掉。它倾向于**拒绝作答**而不是硬猜，
  但阈值（`min_agree`，默认 0.75）需要按你的验证码调。
* **不做扭曲/旋转/粘连**。这类验证码请改用 CNN/CRNN，本项目不碰。
* 通道 2 目前约 60~200 ms/张（枚举宽度 × DP），比通道 1 慢两个数量级。

## 合规使用

本项目是通用图像识别工具。用在什么地方由使用者负责，尤其请注意：

* 只处理**你自己有权处理**的验证码。绕过他人系统的自动化访问控制，可能违反该站点的
  服务条款乃至当地法律。
* 不要用它自动化提交他人账号的身份信息、批量探测账号找回接口、或采集他人个人信息。
* 本文档和示例刻意不含任何具体站点的接口地址与字模 —— 那会把通用工具变成针对特定
  在线系统的攻击工具。
